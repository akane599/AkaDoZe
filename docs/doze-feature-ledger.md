# Doze feature ledger

The service selects existing preferences into `DozeConfig`. The controller reads the actual original, durably saves intent, applies on the control runner, and verifies readback. Exit/restart recovery consumes only that ledger, not current preferences or blocklists. A successful command exit is never the state oracle. Unknown originals do not authorize mutations; unsupported output remains UNVERIFIED.

## Commands and readback

## Maintenance and lifetime

There is no maintenance-specific restore preference in the existing code. Preserve the selected radio groups (Wi-Fi, mobile data, Bluetooth, airplane, location) during deep **or** light maintenance: restore their ledger originals temporarily, retain their entries, and reapply from those same entries on a known idle transition. Current preferences cannot replace originals, including AirplaneTile changes mid-session. Every command checks generation/admission/access; unknown transitions do not authorize reapplication, and watchdog does not run during maintenance. Failed reads leave recovery intent intact.

Existing hotspot and music exemptions remain entry-selection rules, as does focused-app exclusion. Core enter runs immediately in battery-saver → motion restriction → force-idle order; music selection defers only feature/package groups, which require a fresh deep-IDLE readback. Selection times out after 2 seconds. Unknown/failed playback selection conservatively skips radios and location (including mobile data even with Wi-Fi on), while non-network groups and package selection continue. Errors/timeouts are journaled; a one-shot generation/admission gate rejects late or duplicate callbacks. Apps/notifications exclude the app's own package.

SCREEN_ON restores only the ledger-backed BIOMETRICS original when waiting for unlock. Verified restoration durably removes that entry; all other entries remain for USER_PRESENT. No current preference supplies the restore value. Failed load/save/readback preserves recovery debt rather than crashing the worker or claiming completion.

Exit retains the core restore order (sensors, unforce, battery saver), then restores remaining entries in reverse durable apply order. Maintenance restore likewise reverses radio entries; reapply remains forward. Thus airplane is undone before owned radios. `wifi_on=2` remains UNVERIFIED, not normalized to ON: its enabled-in-airplane meaning is not the exact ordinary ON original, and unknown numeric states must not authorize mutation. LIFO fixes the owned-airplane case; externally enabled airplane/OEM readbacks can still leave honest debt.

The pure lifecycle helper sets active before rechecking epoch/screen, exits on charger only for an active screen-off session, and pairs one ENTER at the first verified IDLE (including a later reforce) with one EXIT. Teardown waits at most 4 seconds and all command work shares a 3.5-second deadline; unverified restorations remain in durable recovery debt. A schedule-boundary stop while the screen is off can exhaust that budget and leave apps/radios unrestored until the next service start; this remains an unverified device seam. No installed-package scan or preference-driven feature restore runs at teardown/start.

The old rotation/brightness toggle workaround is removed: it performed unrecorded user-setting mutations on exit. Its preference/string keys remain untouched; SQ-17 owns honest UI availability. Motion restoration is JVM/compile-checked, not device-verified.

## Verification boundary

`SessionLifecycleTest` first reproduced the four reviewed lifecycle assertion failures. Feature/controller/catalog tests cover durable originals, battery-before-force, delayed first IDLE, exact package ownership and notification flags, maintenance cancellation/access loss, root gating, strict legacy originals and API bands. SQ-29 regressions reproduce missing keyguard restore, throwing maintenance load, music core gating/missing timeout wiring, and airplane/radio restore order before the fixes. Pure tests additionally exercise one-shot selection, late callbacks, wake admission/debt, and split core/group entry; source assertions pin Android service wiring, not device behavior. The exact ticket verifier runs unit tests and assembles debug.

The legacy 23–32 notification regex expects `PackagePreferences:` but AOSP dumps print `AppSettings:` (and may omit default importance). That real path is probably always UNVERIFIED; synthetic fixtures do **not** demonstrate platform effectiveness. API-23 `pm default-state` support is also device-unverified: an unsupported command would retain app restoration debt. Real never-connecting MediaController behavior, keyguard biometrics, schedule-boundary teardown, physical device effects, Shizuku uid, OEM dumps, sensor-privacy transactions, notification hidden APIs, and actual radio state were not verified here.
